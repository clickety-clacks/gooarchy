# Windows and input

Run independently in a fresh Scottland login on a capable isolated Wayfire session. Use two ordinary windows with distinguishable titles and one Xwayland window if the candidate ships Xwayland support. Capture layout state and a screenshot or short recording after each change. Input may be physical or a supported virtual input path if it produces the same compositor behavior.

1. **Center and periphery.** Open an ordinary window, move it from the center toward a screen edge, and observe Scottland scale it into the periphery; move it back and verify full center size and keyboard focus. A second window must remain usable. Compare the visible geometry with `scottland/layout-state` when that IPC is present.
2. **Rail widget.** Drop a supported window on a side rail, verify that it becomes a widget without stealing focus from the ordinary window, then restore it to an ordinary window. The window must remain interactive in both states.
3. **Fullscreen and focus.** Make an ordinary window fullscreen, open or focus another ordinary window, and return. Check that the fullscreen window fills the intended output, focus follows the user action, and neither window is lost or incorrectly left as a widget. Repeat after a fresh login if fullscreen persistence is part of the candidate.
4. **Bindings.** Use the installed keyboard shortcuts for the terminal, browser and file manager, then one candidate-specific Scottland or Flavorings binding listed in the release notes. Each must launch the intended action once, keep its visible label where the UI provides one, and leave unrelated keys unchanged. A binding whose target binary/command is not installed is a `FAIL`, not a pass from config text.
5. **Xwayland boundary.** If shipped, open an X11-only test window on a fresh installation and again after an ordinary rerun. It must display, accept input and close without disrupting native windows. Record the installed Xwayland/firmware identities and both observations separately; package presence alone is not the behavior result.
6. **Output change.** On a setup with two actual outputs, move a center window and a rail widget between outputs, disconnect and reconnect a secondary output, and verify usable focus and window placement. If the candidate has no multi-output capability in this environment, mark this step `BLOCKED` with the capability reason and run the other steps independently.

Close only windows created for this run and save the before/after layout observations. The attended per-screen zones check on the target display is a **final-release prompt**, specified in [final-release.md](final-release.md); it does not block source integration or other runbooks.
